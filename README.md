# Stockmok Firebase Foundation

This repository contains the C1 Firebase/data foundation and, on `feature/backend-security`, the B1
security and command foundation. It intentionally contains no frontend and no deployed resources.

**B1 adds `firestore.rules` and the trusted server foundation.** The sentence below about Firestore
starting without a rules file describes C1 and no longer holds: `firebase.json` now points at
`firestore.rules`, so the emulator loads the real ruleset. B1 still exports **zero** callables — command
bodies belong to B2, B3 and B4.

## Local requirements

- Node.js 22
- Java 21 or later for current Firebase emulators
- npm

Install dependencies with `npm ci`, then run `npm run verify`.

## Firebase emulator

The local project id is always `stockmok`. Emulator ports are Auth 9099, Firestore 8080, Functions
5001, Hosting 5000, and UI 4000. Firestore starts without a rules file and therefore allows emulator
reads and writes; this is deliberate for C1 bootstrap work and provides **no Security Rules evidence**.

Start a clean suite with `npm run emu:clean`. The temporary Admin SDK bootstrap exposes only:

- `npm run seed:bootstrap`
- `npm run replay:bootstrap`
- `npm run reset:emulator`
- `npm run reseed:bootstrap`

The scripts refuse missing/non-loopback emulator hosts, a project id other than `stockmok`, production
arguments, and live service-account credentials. They use fixed IDs and timestamps, and the reset script
awaits both official emulator DELETE endpoints.

Canonical `seed` and command-driven replay scripts are deliberately absent. Those names, along with
`T-SEED-01a` and `T-SEED-01b`, remain reserved until the real command layer exists.

Run the evidence tests with:

```text
npm run test:bootstrap:t0
npm run test:bootstrap:replay
```

They prove data shape, arithmetic, reconciliation, deterministic fixture idempotence, and emulator
reproducibility only. They do not prove authorization, Security Rules, command behavior, transactions,
audits, notifications, concurrency, or callable idempotency.

## Security and backend foundation tests (B1)

Two emulator-backed suites, both run through `firebase emulators:exec --only firestore`:

```text
npm run test:rules      # tests/rules/**   — firestore.rules, via @firebase/rules-unit-testing
npm run test:backend    # tests/backend/** — the server guards and the command frame, via the Admin SDK
npm run test:security   # both
npm run verify:security # npm run verify, then npm run test:security
```

They need **JDK 21 or later**; current `firebase-tools` refuses anything older. Point `JAVA_HOME` at a
21+ JDK and put its `bin` on `PATH` before running them.

`tests/backend/**` deliberately uses the Admin SDK, which bypasses `firestore.rules` completely. That is
the point: it proves the guards in `functions/src/guards/**` and the `defineCommand()` frame deny on
their own, because for a Cloud Function the rules do not run.

## Generated indexes

`firestore.indexes.json` is generated by `scripts/generate-indexes.ts`. The implementation contains 35
non-matrix definitions and the generated 32-row DB-CR-038 product-list matrix, for exactly 67 indexes.
Run `npm run verify:indexes` to reject drift. IDX-03 and IDX-19 remain tombstones.

## Functions

The `functions` workspace is a Node 22 codebase holding the B1 foundation — `core/` (Admin app,
transactions, idempotency, audit, notify, `defineCommand()`, the registry, the callable adapter) and
`guards/` (auth, membership, role, owner, tenant, `operationId`). Callable, HTTP, trigger and scheduled
exports stay at **zero** until B2. Do not add a dummy function for emulator smoke testing.
